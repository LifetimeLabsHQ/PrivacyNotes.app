# Threat Model

Last updated: 2026-11-19 (v0.793.1)

This document describes the security assumptions, trust boundaries, and known limitations of PrivacyNotes, for auditors, contributors, and users who want to know exactly what the system protects against and what it does not. It is the one place that says how each protection works and what it leaves open. [SECURITY.md](SECURITY.md) says what each protection does for you, [VERIFY.md](VERIFY.md) says how to check it, and the help answers link here instead of explaining it again.

## System overview

PrivacyNotes is an end-to-end encrypted personal workspace (notes, tasks, journal). A 12-word BIP-39 mnemonic phrase, generated client-side, is the sole root of trust. Every key and secret below is derived from it via HKDF-SHA256 with domain-separated info strings, except the browser extension's logins key, which is random (see "Key derivation"). Two of them carry the design:

1. **Ed25519 signing keypair** - the public key is the user's identity (pubkey); signatures authenticate sensitive API calls.
2. **XChaCha20-Poly1305 symmetric key** - encrypts all note content, attachments, user settings, and note version history before anything leaves the device.

Under self-custody, which every phrase sign-up uses, the phrase, private signing key, and encryption key never leave the client, except a copy of the phrase sealed under a sign-in passkey the user adds, which the server cannot open (see "Passkey sign-in"). The server stores ciphertext, nonces, and operational metadata: the pubkey, device rows with peppered fingerprint hashes (see "Devices and fingerprint hashes"), quota counters, and subscription records. The full user-facing accounting of that metadata, including the identifier-free import counters and the website-icon lookups, is SECURITY.md's "What we measure" section; this document does not repeat it. The server never stores plaintext content.

**Browser extension.** The extension never holds the key that opens your notes: it locks each clip and each note with a key only your apps can open, and one of your apps turns it into a note. The server learns that an account uses the extension, the browser's name and the extension's version (sent when it connects), when a clip arrives, roughly how large it is, and the browser's IP address; it never learns the page. With logins turned on, the server also stores a second encrypted copy of the vault items the extension shows (logins with the private keys of the site passkeys saved in them, credit cards, SSH keys without their private keys) and of the account's bookmarks, under a separate key that opens nothing else, and it sees how many there are and when they change, each unlock, and each pull of that copy (when the popup opens while unlocked, and every 20 minutes). It keeps half of that key and a checker for the extension's PIN or passcode, and counts wrong tries; neither opens the logins without the half that stays in the browser. When you ask the extension to fill a login, it writes that login into the page you are on, and only when the page's address matches the login; a part of the page that comes from another site gets it only when its own address matches too. From then on the page holds what was filled, as it does when you type it, so a script the site loads, or one injected into the site, can read a filled login the same way it reads a typed one. With passkeys offered (a setting, on by default), two content scripts run on every https page, in the top frame only, and do nothing until the page asks the browser for a passkey; from them a page can tell that the extension is connected and offers passkeys. The extension takes the request only when the asking origin matches the tab's address and the relying party id belongs to that site, and a sign-in only after a click or key press on the page; it creates and uses the passkey itself, and counts an unlocked extension as user verification. A new passkey reaches the page only after the sealed inbox row that carries it is on the server, so a passkey a site accepted is never only in the browser. Through the same sealed inbox the extension can change a login, not only add one: a change carries a proof made with the logins key, which only an unlocked extension holds, and without it an app saves the change as a new login; an app applies the change and the login's History keeps the earlier version. Until the next pull, the browser keeps the passkeys and changes it sent in a local store encrypted under the logins key. Residual: while the person clicks on a page, the page gets one answer a minute, for the whole site, on whether the extension holds one of the passkeys it names; a yes opens a prompt the person sees. A save that reached the server after the page stopped waiting leaves a passkey the site never got; it shows in the Vault for that site, which refuses it. Residual: the one-time pairing code is all a browser needs to connect, so whoever pastes it first, within its 10 minutes, sets the PIN or passcode and can read the copy. The app names the browser that used the code while the code is on screen and marks a newly connected browser in Settings > Extension; Remove ends that browser's access, and deletes the clips and logins it sent that no app has opened yet, but not what it already read, and not a passkey or a change to a login it sent, which waits for an app to open it. Removing a browser with logins makes an app change the logins key; each remaining browser then makes a fresh half of the new key at its next unlock and sends it sealed to the inbox key, and a browser too old to do that stays on the old key until it is connected again with a code. Residual: an app version that predates the fresh halves still writes each remaining browser's server half from the half that browser already held, so the removed browser's key together with the server's halves from before and after the change gives the new key. Whoever can write inbox rows with a remaining browser's token (the operator, or anyone with write access to the database) can plant a half of their own and so learn the new key. Residual: while passkeys are offered, page code that runs while the extension reads a passkey request can see the extension's script address in an error stack, so a page can tell which extension handles its passkeys; in Firefox that address holds an id made at install, the same on every site.

**Command line.** The command line tool `privacynotes` connects with a one-time code from Settings. Its config file holds the account's inbox public key and a token that can add notes, with the account id, the token id, the computer's label and the title and time of the last note it sent, all readable. It cannot open, change or delete notes. A note from `privacynotes` is encrypted on the computer that runs it and waits on the server, sealed, until one of your apps opens it; a note that no app opens within 90 days, or before you remove that computer in Settings, is deleted. Anyone who copies the token can add notes to the account until you remove that computer in Settings; the server refuses new notes from it, and new clips from a browser, once the account is at its note or storage limit. The server sees that a note arrived, its padded size and when.

**Quick note on a locked computer.** While the desktop app is locked, a note typed in the Ninja box is encrypted on that computer to the same inbox key and kept there until the next unlock, when the app adds it. It never reaches the server in that form. Residual: a person at a computer where PrivacyNotes runs locked can add notes to the account, but cannot read any.

**Subscribed calendars.** The address of a calendar you subscribe to is kept in your encrypted settings, and each of your devices downloads that calendar itself and shows its events without storing them. The desktop and phone apps download it directly, so the calendar's server sees the device's IP address and when it downloads. The web app downloads it through our Cloudflare Worker, which sees the address and the calendar while the request runs and keeps neither. Residual: in the web app this happens on each download, about once an hour while the app is open, and a private calendar address works like a password for that calendar.

**Clipping a page in the app.** A page you clip, and the pictures on it, are downloaded the same way: the desktop and phone apps download them directly, so the site sees the device's IP address, and the web app and the demo download them through the same Worker route (`/clip-fetch`), which sees each address and what it downloads while the request runs and keeps neither, with no log line that holds an address or a size. For its rate limits the Worker counts downloads and bytes per account public key in windows of a minute and a day, and deletes a counter when its last window ends; SECURITY.md's "What we measure" lists them. Residual: in the web app the Worker sees which page an account clips, and which calendar it downloads, while it fetches them.

**One exception, offered at OAuth signup and preselected there.** In custodial mode the phrase is stored server-side, encrypted under a server-held key, which makes the server capable of decrypting that user's data. Everything below describes self-custody unless stated otherwise; the custodial deviations are specified in "OAuth users" and are the single largest trust boundary in the system.

## Trust boundaries

### Fully trusted

- **The user's device.** An attacker with full device access (OS-level keylogger, memory inspection, code running as the user) can extract the phrase. Out of scope. A copy of the app's stored files taken without that access (a backup, a copied browser profile or app data folder, another account on a shared computer) is in scope: "Local storage at rest" sets out what such a copy yields with and without the app lock.
- **The user's browser/WebView.** We rely on Web Crypto API, IndexedDB, and localStorage behaving correctly.
- **The cryptographic primitives.** `@noble/ciphers`, `@noble/hashes`, `@noble/ed25519`, `@noble/curves` (X25519 for the inbox key, P-256 for the Vault's site passkeys), `@scure/bip39` - audited, widely deployed libraries by Paul Miller. The phrase stored on a device is wrapped with the browser's own Web Crypto API instead (AES-GCM, PBKDF2, HKDF).

### Partially trusted

- **Supabase (server + database).** Sees pubkeys, ciphertext, nonces, timestamps, and the metadata listed above. Cannot read content. A compromised server can delete data, serve stale data, and observe access patterns (which pubkey syncs when, note count, ciphertext sizes). It cannot decrypt notes, and it cannot forge one from nothing, except through the inbox: a row sealed to the account's inbox public key names no sender, and that key is in every pairing code, so the operator, or anyone with write access to the database, who holds it can add notes, clips and logins that the apps take as the owner's. They read nothing. With database write access it can put one of your existing ciphertexts onto another of your rows, or an older one back on its own row; the apps refuse most of these, and "Known limitation: no AAD" below lists the rest.
- **Cloudflare (CDN + Workers).** Serves the frontend bundle. A compromised deployment could serve malicious JS that exfiltrates the phrase - the standard supply-chain risk for any web app. Desktop (Tauri) builds bundle the frontend locally, which mitigates this.
- **Paddle (payment processor).** Receives transaction metadata, no note content. Webhooks verified via HMAC-SHA256.
- **The App Store and Google Play (store payments).** Receive transaction metadata, no note content. An App Store notice is accepted only when its signature chains to Apple's root certificate, and a Google Play notice only when its address carries a secret shared with the Pub/Sub push that delivers it. Neither notice is taken at its word: before it writes, the server asks Apple's or Google's API about the purchase the notice names and acts on the store's answer.
- **BlockBee (crypto payment processor).** Runs the payment page on `pay.blockbee.io` when Pro is paid in crypto, and forwards the coins to our wallet. It never receives the pubkey: our server keeps an order record that maps BlockBee's payment id to it. BlockBee sees the payer's IP address, the coin, the amount and the paying address, and the payment is public on its blockchain, where each sale forwards to the same receiving address of ours. Lightning payments wait with BlockBee's Lightning provider until a daily payout. Its webhooks are signed with a 1024-bit RSA key, so Pro is granted only after BlockBee's own API, queried with our key, confirms the payment.
- **The passkey provider that holds a sign-in passkey.** It can release the recovery phrase to whoever controls it (see "Passkey sign-in").
- **The map host (`maps.privacynotes.app`, Cloudflare R2).** Serves the world map in the window of a place you set on a note (when you open that window), and a map in a note's text (each time that note is open, which includes the Welcome note every new account starts with), in the demo too. Each map read carries the device's IP address and the byte range of the tiles around the place, so the host can tell which area was looked at. It also serves one list of places per language, downloaded whole when a place window opens for typing, or on a phone when a new note adds the device's location by itself; the place search runs on the device, so the host learns the app language, not the search. It never receives the note, its text or the place's name. Otherwise a place leaves the device only inside the encrypted note. "Open in OpenStreetMap" hands the coordinates to openstreetmap.org in your browser, as any link you open does.
- **The plugin host (`plugins.privacynotes.app`, Cloudflare R2).** Serves the optional plugin downloads (models, engines and language files) to a device that turns a plugin on (see "Plugins"), so it learns the device's IP address and which plugins and languages it downloads, and, as any server a browser downloads from, the app's address and the browser's user agent. It never receives a note or anything from one.
- **The release host (`releases.privacynotes.app`, Cloudflare R2).** Every desktop and phone app asks it for updates, and the website's download buttons ask it for the latest version numbers, so it learns the device's IP address and platform. The update policy file can tell a store, Android or `.deb` build to stop sending changes to the server until it is updated. The app takes it only when the file names that build's channel and carries a valid signature by a release key built into the app, and it refuses a file issued before the one it holds. Someone who controls the release host can still withhold the file, or give a build that holds no policy yet an older signed one. Versions of the app released before this check still accept an unsigned file.
- **The file store (`files.privacynotes.app`, a Cloudflare Worker in front of a Cloudflare R2 bucket in the EU jurisdiction).** Holds encrypted pictures and files as a second store beside Supabase Storage (see "Encrypted attachments"). For each object it sees the account's public key and a random id (the object's name), the size, the upload time, a hash of the ciphertext and a random id of the upload; for each request, the device's IP address and the session token. Its logs keep the route, the status, the size and a short prefix of the public key. It cannot read content. A compromised Worker can withhold, replace or delete files, and can use a token passing through it the way a stolen session can, which on a custodial account without two-factor sign-in includes fetching the stored phrase (see "Custodial (keep it simple)"). Under self-custody it cannot decrypt a file or forge one that opens. The ciphertext passes through a Cloudflare data center near the device on its way to the bucket; it is stored only in the bucket.
- **The backup provider (a second provider in the EU).** Holds a copy of each encrypted file in the file store under the same name, made by the Worker from the ledger in the night after the file is stored. It sees the name (public key and random id), the size, the SHA-256 of the ciphertext and the time of each copy, never the content or a key. Its bucket keeps only the last version of an object, so a removed or replaced copy does not stay there as an older version beyond the provider's daily clean-up.

### Untrusted

- **The network.** TLS everywhere; content is encrypted before transmission regardless.
- **Other users.** RLS policies enforce strict pubkey isolation.

## Cryptographic design

### Key derivation

```
BIP-39 phrase (128 bits entropy)
  → mnemonicToSeedSync (PBKDF2-HMAC-SHA512, 2048 iterations, salt "mnemonic", passphrase empty)
  → 64-byte seed (a stretch of the 128 bits above, not new entropy)
  → HKDF-SHA256(seed, salt=none, info="privacynotes-signing-v1")       → 32-byte Ed25519 private key
  → HKDF-SHA256(seed, salt=none, info="privacynotes-encryption-v1")    → 32-byte symmetric key
  → HKDF-SHA256(seed, salt=none, info="privacynotes-auth-password-v1") → 32-byte session credential
  → HKDF-SHA256(seed, salt=none, info="privacynotes-local-at-rest-v1")  → 32-byte local sealing key
  → HKDF-SHA256(seed, salt=none, info="privacynotes-fp-pepper-v1")      → 32-byte fingerprint pepper
  → HKDF-SHA256(seed, salt=none, info="privacynotes-clip-inbox-v1")     → 32-byte X25519 inbox key

Below the branches:
  symmetric key → HKDF-SHA256(info="privacynotes-ext-logins-wrap-v1")  → wraps the logins key in the synced settings
  symmetric key → HKDF-SHA256(info="privacynotes-ext-logins-id-v1")    → keys the row ids of the logins copy
  inbox key     → HKDF-SHA256(info="privacynotes-clip-item-id-v1")     → keys the ids of items made from inbox rows
  each inbox row: X25519(one-time key pair, inbox public key)
                → HKDF-SHA256(info="privacynotes-clip-seal-v1")        → that row's key

Random, not derived:
  logins key P (32 bytes, made by an app, split between a browser and the server)
                → HKDF-SHA256(P, info="privacynotes-ext-loginedit-proof-v1") → the proof key of a login change
```

The other four branches each have one narrow job: the session credential is a login secret (below), the local sealing key seals the device's own database ("Local storage at rest"), the fingerprint pepper keys the hashes that let the device limit recognize a returning device, so the hashes of one device differ between accounts, and the inbox key opens what a browser extension or the command line sealed to its public half (the "Browser extension" paragraph above). Of the four, only the inbox key opens anything the server holds: the inbox rows waiting there.

**HKDF salt is omitted.** Per RFC 5869, an absent salt is a zero-filled string. Acceptable here: the input keying material is the 64-byte seed above, which carries the phrase's 128 bits of entropy, and domain separation comes from the info strings. An explicit salt could be added in a future derivation version but would not meaningfully improve security.

**The session credential is a login secret, not a key.** Returning devices re-mint their Supabase session by password grant against the account's existing auth user, using the auth-password HKDF branch (hex-encoded) as the password and the deterministic identifier `<pubkey>@phrase.privacynotes.app` as the login email. That address is an identifier in email shape: the domain receives no mail, and the server derives it from the signature-verified pubkey, never from client input. The server stores only a bcrypt hash of the credential; recovering the seed from it is not possible. Holding the credential grants what a session grants: reading, overwriting and deleting the account's ciphertext on the server, never its plaintext. Because it comes from the phrase, no sign-out or device removal ends it: each password grant makes a new session. A session that is not refreshed for the inactivity timeout (see the known limitations of the custodial section) ends; a device that holds the phrase makes a new one by the same grant. Anonymous sign-in makes an account's first session, and stands in when the server refuses the credential (an account older than it, or the email provider switched off); the pubkey link then attaches that session to the account only with a signature from its key.

### Encryption

- **Algorithm:** XChaCha20-Poly1305 (256-bit key, 192-bit nonce, 128-bit tag).
- **Nonce:** 24 bytes from `crypto.getRandomValues()` per encryption. The 192-bit nonce space makes random collisions negligible (~2^96 birthday bound).
- **Payload:** the note's JSON fields - title, body, tags, note type, metadata flags, journal mood-tracker entries, and a place you set on a note - are encrypted as a single blob. Health-adjacent data (mood tracking) sits inside the E2E envelope like everything else. The server stores base64 ciphertext and nonce.

**Known limitation: no AAD, and the row binding that stands in for it.** The cipher authenticates no associated data on the server's rows, so a party with write access to the database or the bucket can put one authentic ciphertext of an account where another of the same account belongs (a cross-account swap fails, because the key differs). The apps carry a binding inside the encrypted payload instead: every note they write names its row id, its table (a live note or a history version) and the stamp the write sends, and, once no supported app version writes without it, every file they write will name its own id, in an id form that says the file carries one; every app reads that form already. A reader refuses a note payload that names another row, table or stamp: the device keeps its own copy and lists the row under "Notes this device can't open", where the person can send this device's copy again or delete the note. A note payload older than the clean copy a device holds is a rollback: that device keeps its copy and sends it back over the older one, and a device with an unsynced edit takes nothing from it. A file whose id says it carries one opens only with its own id inside. What stays open:

- A device that never held the newer text (a new device, a fresh sign-in, one offline the whole time) takes an older ciphertext as the note.
- A note payload written before the binding carries none and is taken as before. The apps refuse one written after a cutoff once no supported app version writes such payloads; the server then also refuses a note write from an older app.
- Two genuine versions of a note with the same stamp cannot be told apart.
- A history version written before the binding can be added as a version of any note of the account. The person sees it in History and restores it only by choice.
- A file written before files carry their id can be swapped with another file of the same account.
- A party who removes a delete marker can put the note's last ciphertext back, and its binding matches.

All of these reuse ciphertexts the account already has: they never yield plaintext, and the precondition already lets that party delete or withhold data, which the Supabase entry above counts. When a sync takes such a text over a clean note, the device keeps the text it replaced (see "Replaced text" under Sync, conflicts, and deletion). The full fix is a versioned AAD over the row or object identity and a format migration of every stored ciphertext and every client. It is not scheduled.

### Encrypted attachments

Images and file attachments use the same primitive via `encryptBlob` (`shared/src/blob.ts`): raw bytes encrypted under the user's symmetric key, 24-byte nonce prepended to the ciphertext. The original filename, MIME type, and size are encrypted inside the blob. The server sees an opaque object at path `<pubkey>/<uuid>`, in one of two stores while files move between them: a private Supabase Storage bucket in Zurich, where RLS restricts each user to their own path prefix, and the file store in the EU (see "Trust boundaries"), where current apps upload. Older files, and uploads from older app versions, stay in Supabase Storage until they are copied to the file store, checked by size and SHA-256, and removed from Supabase Storage. A file in both stores counts once.

**The file store.** The app sends every file request to the Worker, never to the bucket. Before every act the database checks the caller's session with the same gates as the row policies and names the object from that session, so a request reaches no other account's files. The bucket refuses an upload whose ciphertext does not match the hash it was sent with. The database keeps a ledger row for each file in the file store (the name, the size, the hash, the format and the times) and takes a ledger write only from the Worker. Current apps also reach files still in Supabase Storage through the Worker, which passes the person's token and the ciphertext on.

**Delete and the trash.** A delete in the file store moves the object to a trash in the same bucket; outside account deletion, nothing the app or the server's clean-up does erases a file outright. A file the app deletes itself is kept 30 days, and a bucket lock stops anyone from erasing it for the first 7. A file less than an hour old, a delete beyond a size limit of the account's trash, and every delete by the server's purge are kept 3 days, with no lock. A file deleted from Supabase Storage is removed there at once.

**The backup copy.** Twice a night, a server job sends the names that the ledger added or changed to the Worker, which copies those objects to the backup provider. A name gone from the ledger for 30 days is removed there by the next run, and the provider erases the bytes within a day or two after that, so a deleted file can stay in the backup for up to 35 days after it leaves the file store. Until its removal, the name stays in the database too. A dead man's switch deletion queues the account's files for the server's purge, which takes a file five days after it was queued at the earliest; the file then has the 3-day trash and the 35 days of the backup, so its copies can stay up to 40 days after the deletion.

**Account deletion.** The Worker deletes every live, orphaned and unlocked trash object of the account at once. Objects inside their 7-day lock stay until the trash removes them, up to 30 days after their own delete. The account's backup copies are removed by the first run of the backup job that starts an hour after the deletion, so within a few days.

Residual: someone who obtains the Worker's secrets can delete files from the file store, outside the locked trash, and from the backup, and with a valid session can write false ledger rows and upload counts for that session's own account. They read nothing: no key in the Worker opens a file.

Residual: a file that an older app version deletes is removed from Supabase Storage only. If the file store already holds a copy, that copy stays, counted toward the account's storage, until a current app version of the account checks its files.

Residual: an upload still running when its account is deleted can leave its ciphertext in the bucket. The account's deletion refuses the upload's record, so the object is moved aside after 7 days and erased after 30 more.

Residual: the storage service checks an upload link against these rules when the link is made, not when it is used, and a link stays valid for two hours. A session can make links ahead of time, so for up to two hours after that session is revoked or the account is banned, its links can still add or replace objects under the account's own prefix. They read nothing and reach no other account's prefix. The app itself never makes such links.

Residual: for an account without account management or two-factor sign-in, the row policies look at the session only to refuse one whose device was removed from elsewhere (Devices and fingerprint hashes, below). A sign-out removes its own device without marking its session, and ends that session at the sign-in service when the request reaches it. A copy of the session taken before the sign-out keeps its access token, which works for up to an hour; a sign-out that never reached the server, and a session with no device bound to it, keep reading and writing the account's rows for as long as the sign-in service lets them refresh.

### Burn notes (one-time shares)

A burn note is encrypted client-side with a fresh random key that exists only in the share URL's fragment (`/burn#id=<uuid>&k=<hex>`). Fragments are never sent over HTTP, so the server holds ciphertext it can never decrypt, with no link to any account (creation is anonymous). Opening the link calls a consume-once RPC that deletes the row and returns the ciphertext in one statement; the table has no SELECT policy, so rows cannot be listed or re-read. Unopened notes are purged when the lifetime the sender picked runs out, at most 7 days.

### QR sign-in and phrase handoff

Adding a device via QR shows a code on the trusted device that holds the phrase's BIP-39 entropy as `PNQR1-` followed by upper-case hex. It is not a link and has no URL scheme, so a phone's camera app has nothing to open and no installed app can claim it; the new device reads it with "Scan QR with camera" or an uploaded image on the sign-in screen, which never navigates. That scanner also reads the older QRs: a link with the phrase in its `#phrase=` fragment, and the bare words. A page that opens with a `#phrase=` fragment (an older QR read by a camera app) clears it from the address bar and does not sign in; the sign-in screen says the browser history may now hold that link, and the marketing host sends the visitor on to the app host with no fragment. Residuals: a camera app can show the code as text and offer to copy it or search the web for it, and one tap on that sends the phrase, in another form, to the clipboard or a search engine and its history. An older QR opened through a camera app has written the phrase into the browser history and session-restore data before the page runs, and history sync can carry it off the device; delete that visit. Installed apps from before the code keep drawing the link QR until they update, and their scanners do not read the code. Any valid code is a valid phrase: scanning a stranger's code on a device with no local data and confirming signs that device into the stranger's account (the words show first; a device that holds another account's data asks before it clears it). The QR itself is equivalent to the phrase while displayed, and so is a saved image of it - treat it as a secret.

### Challenge-response authentication

Device registration, pubkey linking, custody changes, device removal and account deletion use Ed25519 signatures over structured challenges (e.g. `link:<authUid>`, `register-device:<authUid>:<deviceId>`). The operation and the `authUid` are inside the signed string, so a signature cannot be moved to another operation or another account, and every signed call also needs a live session for that account. Custody changes, device removal and account deletion also sign a one-use server nonce bound to the session and the exact request. Residual: linking, device registration and the cancel or change of a storage plan carry no nonce or expiry, so a captured signature of any of them verifies again for the life of the account, and while older app versions are supported the server also accepts the older signatures of custody storage and removal, device removal and account deletion, which carry no nonce. Someone who holds a live session of the account and such a captured signature can repeat that one operation.

### Passkey sign-in

A signed-in device can add a passkey that signs in on a new device. The device asks the passkey for its PRF output over one fixed input, derives an AES-GCM-256 key from it with HKDF-SHA256, and encrypts the recovery phrase, padded to 256 bytes, with the passkey's credential id in the additional data. The server stores that ciphertext, the passkey's public key (ES256 or RS256), its credential id and relying party id (the host it was added on, `use.privacynotes.app` or the public beta `beta.privacynotes.app`, never the apex domain, so script on another subdomain cannot ask for the PRF output, and a passkey answers only on its own host), the account's signing key at the time, the times it was added and last used, and a name the device sealed under the account's content key (XChaCha20-Poly1305). To sign in, the server issues a one-time challenge that expires after two minutes, checks the passkey's signature and its user presence and verification flags, and returns the ciphertext; the device decrypts the phrase and signs in with it as if it had been typed, so two-factor sign-in still applies. The server never holds the PRF output, so it cannot read the phrase from this copy (an account in server custody has its separate custodial copy as before). Residual: whoever controls the passkey (the passkey provider account it syncs through, such as Apple, Google or a password manager, or a device that can use it) can obtain the recovery phrase; where two-factor sign-in is on, the code still stands between the phrase and the account's data on the server. Adding a passkey needs the app's PIN or passcode where one is set, a recent two-factor check where 2FA is on, and the phrase's signing key over a one-use server nonce bound to the session and a digest of the whole request; removing one needs the same signature and two-factor check. A phrase change retires every passkey added before it: the server deletes such a slot when it is next used.

### Phrase change

An account the server allows to change its phrase re-encrypts its notes and settings under keys from the new phrase. Until every row is rewritten, each device keeps the replaced phrase's keys to open older rows. It takes no note or sealed delete that those keys open when the server changed it after the phrase change, by the server's own change time, which a session cannot set; and a settings row opens only with the key its label names. So the holder of the replaced phrase cannot pass off a new note or delete as the owner's with a session alone. Residual: the operator, or anyone with write access to the database, who also holds the replaced phrase can set that change time.

## Local storage at rest

**Note content is sealed at rest on the device.** Rows in the `notes` store carry a version marker and one XChaCha20-Poly1305 ciphertext holding title, body, tags and tracker data, and beside it a second, smaller one holding the sync base (a fingerprint of each field of the version the device last synced, which the merge compares); the sealing key is a dedicated HKDF branch off the phrase (`privacynotes-local-at-rest-v1`), derived on unlock and never stored. The AAD binds each ciphertext to its table and row id, so a blob moved between rows or tables fails authentication. The server's rows carry a weaker binding, inside the payload (see "Known limitation: no AAD"). The same seal covers the parsed-document cache and, in raw-bytes form, the decrypted image and attachment caches (the attachment's filename metadata seals beside its bytes); the in-flight edit stash in localStorage seals under the same key. Sealing is enforced in one place - a middleware under the local database layer - and a CI test drives the write paths it lists, then inspects every table and every app key in raw storage, so a new store is covered at once and a new writer once the test drives it.

What a copy of the device's storage yields depends on what was copied and on the app lock:

- **A copied localStorage file alone, or a script-level dump,** carries ciphertext and the phrase envelope without its key, so neither the notes nor the envelope open from it. The lock's own wraps are in that file too where this device holds them: the account's PIN or passcode wrap while this device's lock is on or while it keeps no phrase at rest that opens, and the key of a biometric enrollment that is not bound, which stays after the lock is turned off; they open the phrase as the next two bullets set out; so is the sign-in session (end of "Local phrase-at-rest: biometric and PIN wrapping").
- **A copy of the whole browser profile or app data folder, without the app lock,** also carries the bytes of the key that opens the envelope in a browser, on a Mac without a Secure Enclave and on a Linux desktop without an unlocked keyring (see "The phrase itself is wrapped" below), so a parser of the browser's files recovers the phrase, and with it the notes. In the other apps that key stays with the device, so the envelope in such a copy opens nothing on another device or account. The copy still carries the lock's own wraps where this device holds them: the PIN or passcode wrap is the account's, and a trusted device keeps it outside the sealed settings while its own lock is on, or while it keeps no phrase at rest that opens. In the apps whose device keeps the key, that wrap is sealed behind the same key, so the copy alone cannot search it; elsewhere, on such an account, the copy opens the phrase at the offline search cost of that secret (see "PIN protection"); a biometric enrollment that is not bound to secure hardware or a passkey stays after the lock is turned off and opens the phrase without a search (see "Local phrase-at-rest: biometric and PIN wrapping"). The copy also holds the sign-in session (end of the same section).
- **The same copy with the app lock on** carries no envelope: the phrase is stored only under the lock's own wraps, the one under the PIN or passcode, bounded by the offline search cost of that secret (see "PIN protection"; in the apps whose device keeps the key it is sealed under that key as well, so the copy alone cannot start the search), the biometric wrap, or both. Biometric unlock that is not bound to secure hardware or a passkey keeps its key in the same storage (see "Local phrase-at-rest: biometric and PIN wrapping"), and the lock is a setting of each device, so it covers only the devices where it is on (same section). The lock does not cover the sign-in session (end of the same section).

Outside the app's own storage, after an older sign-in QR was opened through a camera app, the browser's history can hold that link with the phrase in it (see "QR sign-in and phrase handoff"). Fields the indexes and sync need stay readable on the row: id, timestamps, `dirty`, `deleted`, `trashed`, `starred`, `locked`, `pinProtected`, `archived`, `type`, `folderId`, and the push-echo nonce - which is to say an attacker with the files still learns which rows exist, when they changed, and which are vault items, without reading any of them. Server-side these fields travel inside the wire ciphertext; locally the indexes need them.

Known residuals, deliberate and accepted: existing rows seal on the device's first unlock after the update that introduced sealing (no key exists before unlock, so the backlog waits); browser storage engines keep superseded values in free pages until compaction, so stale plaintext fragments can outlive the sweep for a while; the deduplication indexes store content hashes (an equality check against a known file, not content); the site icon cache (a separate IndexedDB database) shows how many icons it holds and their sizes, image types and times, while each icon is sealed under the local sealing key and found by an HMAC of its address under that key, so the domains in links and vault logins are not readable in it, and with no key on the device it is neither read nor written; the readable part of the local settings cache holds only what the lock screen and the boot read before any key exists (the app lock switch and its windows, the PIN's salt and hash, and two counters), and every other setting, one the app does not know included, is sealed beside it; the theme and layout choices are kept in keys of their own, readable for the first paint; a History version waiting for the server is ciphertext under the account key, kept with the note id, its time and a hash of its content keyed under the local sealing key, so a copy of the files cannot test a guessed text against it; on a phone the app keeps the item id and the time of each alert it handed to the system; the custom theme in use keeps its code, name included, readable on the device, so the first paint needs no key; the day ledger seals its counts of writing, and keeps readable only the days on which this device counted a write; the account panel cache holds user-entered device names and quota figures; an old sealed blob of the same row re-authenticates forever, so a disk-level rollback of one row to an earlier sealed version is undetectable (the format carries no freshness counter); the Markdown folder pillar edits the user's own files on their own disk, outside the seal by design; an item shared into the phone app from another app's share sheet waits outside the seal until the app is next signed in and unlocked, then is sealed and deleted from the inbox (on iOS the inbox is an app-group folder whose files carry complete data protection, so the OS keeps them encrypted while the phone is locked; on Android it is the app's private data folder); calendar alerts on a phone are handed to the operating system ahead of time so they ring while the app is closed, and with "Show titles in reminders" on, each alert handed over while the app lock is off has its item title and folder name held by the system's notification scheduler, outside the seal, until the alert has rung and been cleared or the app schedules it again (an alert scheduled while the app lock is on, and always one for an item behind the PIN, carries only "Reminder" and its time; one handed over before the lock was turned on keeps its title until then); and the throwaway demo database stays plaintext because its keys derive from a public constant. Process memory is out of scope while the app runs - an app that shows notes holds notes. With the app lock on and no phrase stored on the device, locking the app reloads the page after the last edit is saved, so the phrase, the keys and the decrypted notes lose their last reference and the app starts again behind the lock with nothing open. A reload drops references; it does not overwrite the bytes, and the browser or the app's web view may keep the same process, so a memory read taken soon after can still find them. A browser that is offline, a device that keeps its phrase at rest, and a lock that comes while an import runs keep the page and cover it with the lock screen until the unlock, or for an import until it ends. Across the reload the tab keeps, in its session storage, the id of the open note and the time of each coming reminder with the text a lock screen may show (such as "Reminder" and the time, never a title). The real boundary for a lost or stolen machine remains OS full-disk encryption and screen lock, which the app cannot implement and should not imply.

**The phrase itself is wrapped.** Without the app lock, the stored recovery phrase is an AES-GCM-256 envelope in trust-aware storage, encrypted under a non-extractable WebCrypto key that IndexedDB keeps as a key object (`phraseAtRest.ts`). "Non-extractable" is a script-API property, not hardware: the browser never hands the key's bytes to script, but it writes them into its own IndexedDB files, so a copied localStorage file alone does not open the envelope (while this device's lock is on, or while it keeps no phrase at rest that opens, it keeps the account's PIN or passcode wrap, so such a copy is bound by that secret's strength; the copy bullets above list what else it holds) and a copy of the whole profile or app data folder opens the envelope. An attacker who can run code in the app's origin calls the key directly, and one with the live browser profile on the same machine boots the app signed in. In the apps the key comes from the device instead: a key the operating system keeps outside the app's files seals a random 32-byte secret, the envelope stores only that sealed copy, and HKDF-SHA256 over the secret gives the AES-GCM-256 key, which is never stored. On Apple devices it is a Secure Enclave key that only that device's enclave can use, from the first unlock after a restart; on Android an AES key in the Android Keystore; on Windows an RSA key in the PC's TPM (the Microsoft Platform Crypto Provider) whose private half never leaves the chip, or DPAPI, which ties the secret to the Windows account, on a PC without a usable TPM; on Linux an item in the system keyring (the Secret Service, such as GNOME Keyring or KDE Wallet) that the login unlocks. None of them asks for a biometric or a password (a Linux keyring that is still locked shows its own unlock dialog), so code that runs as the user on that device opens the envelope as the app does, and on Linux, and on a Windows PC without a TPM, a copy of the disk together with the account's login password opens it too. On Apple devices, Android and a Windows PC with a TPM the key never moves with a backup, so a device restored from one asks for the phrase once, and so does a PC whose TPM was cleared. On Linux and a Windows PC without a TPM it follows the login account instead: a disk image or profile backup restored with the same login password opens the envelope, and so does a Linux keyring whose password is empty, or a password manager that serves as the keyring and syncs its file elsewhere. Where the app has no such key (a Mac without a Secure Enclave, a Linux desktop without a keyring, or one whose keyring is locked when the phrase is stored) it uses the browser key above. The phrase is never written as plain text: on a browser without working IndexedDB or WebCrypto, the app tries once more and then stores nothing, so the session lasts only until the tab reloads or closes, and a banner says so (where the device holds a PIN, passcode or fingerprint wrap, the next start shows the lock screen instead). A plain value that an older version wrote stays in storage until a wrap works, because removing the only stored copy could strand someone who never wrote the words down, and Settings > Security > PIN warns while it holds (the app lock takes it out of storage). Installs that predate the wrap migrate on their next boot, and an app envelope under the browser key moves under the device key on its next start.

An attacker who can run code on the device (malware, a malicious extension with the right permissions, anyone at the unlocked machine) reads notes through the same door the app does; that is out of scope (see "Out-of-scope threats"). The per-note lock and PIN-protect flags are gates at the client's trust level, not per-note cryptography (see "Lock / PIN-protect notes").

Sign-out clears the local database (`clearLocalDatabase`), including the parsed-document cache and the separate favicon cache, after it removes the phrase, the biometric wrap and the PIN wrap; that wipe deletes by key on the sealed tables, because it runs after the seal key is zeroed. A sign-out the user chooses first uploads unsent notes and settings with no time limit, and asks before it goes on when that upload fails (`signOutUpload.ts`). A forced sign-out (device removed, session gone, device limit) keeps the unsent rows, and the notes whose last typing was not yet saved, through the wipe, still sealed, with no phrase left on the device to open them. A settings change it keeps stays without the PIN wrap and the PIN's salt and hash in its readable part, which the next sign-in takes from the server again (in the apps its sealed part, which opens only with the phrase, can still hold the wrap), and the copy an untrusted tab keeps in memory goes on every sign-out. A device removed from another device is signed out and wiped this way at its next start too: the server brings a removed device back only for a sign-in made on it by hand, never for its own automatic start or a lock screen unlock. The automatic backup setup, the list of backup files this device wrote (name, time, size, item count) and its run log stay in localStorage after a sign-out, so the same person signing in again keeps them; they hold no note content, and the app deletes them when a different account signs in on the device. The account id the device last used and its sign-in log (the times of the last sign-in events, no secret) stay as well. Account deletion (`deleteEntireLocalDatabase`) drops everything.

### Plugins

A plugin (Settings > Plugins) is off until the user turns it on. Its files come from the plugin host, and the app checks each file against a pinned SHA-256 before it loads. A plugin reads notes only on the device and sends nothing anywhere. What it works out, such as the meaning vectors of Smart connections, a picture's text or a transcript, stays in memory until the user adds it to a note, and is dropped when the app locks. In the iOS and macOS apps, some plugins use Apple's on-device engines instead, and the app passes them the data in memory. Apple serves the speech models those engines use, so Apple learns the device's address and the language when one is downloaded.

Compiled code (WebAssembly) runs only in the plugin worker, except in the Linux app (below). The plugin worker's policy allows WebAssembly, but no JavaScript `eval` and no network at all: the app fetches and checks the files and hands the worker their bytes. The policies of the app's pages and of its other workers allow no WebAssembly. The Linux app's web view (WebKitGTK) does not enforce that one rule, so on Linux the page and every worker of the app can compile WebAssembly. This matters only to code that already runs in the page or in one of those workers, and the rest of their policy, such as the ban on `eval`, still holds that code.

Residuals: the worker's policy limits where data can go, not what it can read; it shares the app's storage on the device, including the stored keys, which code in it could use but not send anywhere. Compiled code is harder to review than JavaScript, so its review rests on the pinned source version and hash. The plugin host learns the device's IP address and which plugins and languages it downloads. Cached plugin files and a per-device flag show that a plugin was used on this device until the user removes them.

### Devices not marked as trusted

Phrase sign-in asks whether to trust the device ("Trust this device", ticked by default); an OAuth sign-in always trusts it. On a device that is not trusted, the wrapped phrase envelope and the auth session are kept in the page's memory and never written to `sessionStorage` or `localStorage`, so a reload, a closed tab or a browser restart asks for the phrase again. App lock and biometric unlock cannot be switched on there. Neither the PIN wrap nor the PIN's salt and hash is written to that device's disk: the settings cache withholds those fields, the PIN hash cache and the tab's copy of the wrap stay in the same memory (`pin.ts`, `trustStorage.ts`), and a PIN set there is wrapped in memory for the account only, so the device holds nothing to search offline. The PIN lockout counter stays in `localStorage` on purpose; it holds a count, no secret.

The sealed local database stays on disk until the next start of the app in that browser profile with no session and no open sign-in, which removes it as a forced sign-out does: rows the server has not confirmed, and notes whose last typing was not yet saved, stay as ciphertext for the same phrase's next sign-in. A browser without the Web Locks API keeps the database. Its sealing key derives from the phrase and is never stored, so without the phrase the rows are ciphertext. Signing in to a different account in the same browser wipes it first. Until that start the readable residuals listed above (the local settings cache, the days of the day ledger, the account panel cache) stay on the device as they do on a trusted one, and the days of the day ledger stay after it.

Memory stays off the disk only while the operating system does not swap or hibernate it, and a browser can keep a closed tab's process for a while. The server keeps the sign-in session of a closed tab until its inactivity timeout, with no copy of its tokens left on the device. While the tab is open, the device-trust limits above apply in full: an attacker who can run code in the open tab reads notes the way the app does. On a shared machine, use a private window and close it when done.

## PIN protection

The app lock secret is a 4-digit PIN or, optionally, a passcode of 8 to 256 characters that is not only digits. Its offline bound depends on which: a PIN is 10,000 values, brute-forced in minutes to hours by anyone holding the stored material, regardless of iteration count; a passcode raises that cost with its length and alphabet. The phrase's wrap under this secret is the account's and travels inside the encrypted settings; a trusted device keeps a copy outside them only while its own lock is on, or while it keeps no phrase at rest that opens. In the apps whose device keeps a device key (see "The phrase itself is wrapped"), that wrap is sealed at rest behind it: the lock's own copy and the one a phrase change keeps for a moment under the device key, the settings cache's copy under the local key, which comes from the phrase. A copy of the storage still holds the PIN's salt and hash, so it can find the PIN itself in that time, but the PIN opens the phrase only on the device. A restore on another device, or a reset of the device's key store, then asks for the phrase once. Residuals: older plain copies that a storage engine has not yet compacted away, a wrap written before the device's local key exists at a start, and a seal that failed, which the app logs and repeats at the next write or start. With the app lock armed, the phrase is stored wrapped under this secret, under biometric unlock, or under both (see "Local phrase-at-rest: biometric and PIN wrapping"), and note content at rest is sealed under a phrase-derived key, so where the secret's wrap is the only one, the secret stands at the end of a real cryptographic chain for file-access attackers, within that bound. Users needing more than the secret can resist should rely on OS-level device encryption and screen lock.

### Implementation

- **Hash:** PBKDF2-SHA256, 600,000 iterations, a random salt (16 bytes for a PIN, 24 for a passcode; the length records which), constant-time comparison. The secret is normalized to Unicode NFC before derivation.
- **Legacy hashes:** PINs set before the iteration bump used 100,000 iterations. Such a hash still verifies; after the next check with the PIN, and once that device's settings sync has read the account's settings, it is replaced by a hash at 600,000. A changed PIN or passcode is hashed at 600,000.
- **Storage:** hash and salt in `UserSettings` (encrypted, synced) plus a local cache, in `localStorage` on a trusted device and in the page's memory on one that is not; per-tab session unlock with a configurable timeout. When two devices both changed the PIN since their last sync, the server's version wins and the other device says once that its change was not saved.
- **UI lockout:** 5 consecutive failures lock PIN entry for 30 seconds, doubling on each further failure, up to one hour. The counter lives in localStorage (survives tab close) and is shared across every surface that asks for the PIN or passcode, so attempts cannot be split across views. This blocks casual in-browser guessing only; it does not slow the offline attack above.

### Lock / PIN-protect notes

The `locked` and `pinProtected` flags live inside the ciphertext and are enforced client-side only; any client holding the phrase decrypts everything regardless. Deliberate: a second, PIN-derived key would make those notes unrecoverable on a forgotten PIN. These are organizational privacy features, not cryptographic access control. A note behind its PIN still shows its title, tags, folder, dates and marks in the lists. A protected section (the `protectedViews` setting, in the encrypted, synced settings) is the same kind of flag for every item of one type: it hides those items from every list and search until the PIN or biometric unlock opens it; a reminder for one still rings, as "Reminder" and its time. An app version that predates the setting, and the browser extension, which has its own unlock, do not apply it.

### Local phrase-at-rest: biometric and PIN wrapping

On a trusted device the phrase is stored locally (as the wrapped envelope described in "Local storage at rest") so the user can unlock without retyping it. Two optional features replace that envelope with a user-secret wrap. The app lock, its re-lock window and the PIN's re-ask window are settings of each device and do not sync. Enabling app lock removes the envelope on that device, and the post-unlock sign-in never writes it back while the lock is armed. A device where the lock is off keeps its envelope: in a browser, on a Mac without a Secure Enclave and on a Linux desktop without an unlocked keyring a copy of that device's storage opens the phrase, and in the other apps only that device opens the envelope (see "The phrase itself is wrapped"). The lock's own wraps can stay beside it: while the account has a PIN or passcode wrap, a trusted device keeps it in its sealed settings, and outside them only while its own lock is on or while it keeps no phrase at rest that opens, and turning the lock off leaves this device's biometric enrollment in place, so a copy of that device's storage carries whichever of the two exists (see "Local storage at rest"). A device that signs in copies the lock setting the account holds with its first settings sync; when that setting is on, the device removes its envelope once the account's PIN or passcode wrap has arrived there (`syncPinWrap` in `pinRecovery.ts`). Until then, and when the account holds no PIN or passcode wrap, the envelope stays. A boot-time rewrap of an install that predates the envelope can, rarely, write it back after the strip. The secret's wrap and an unbound biometric are convenience gates at the device's trust level:

- **Biometric unlock.** In the apps, the device's secure hardware releases the secret the wrap key comes from: on Apple devices a Secure Enclave key, whose sealed copy the app stores and which only that device's enclave can use; on Android a Keystore key that needs a strong biometric for each use; on Windows a Windows Hello key, whose signature over a stored random challenge is the secret; Windows keeps that key in the PC's TPM when it has one and otherwise in software, so on a PC without a TPM that key resists a copy of the disk only as well as Windows protects a software key. The app asks Windows, with no prompt, whether the PC has a TPM it can use, and where Windows reports none, Settings on that PC says that the key is kept in software; the app does not learn where Windows put this key, so a PC whose TPM holds no Windows Hello key shows no such line. HKDF-SHA256 over the secret gives a non-extractable AES-GCM-256 key that wraps the phrase, and neither the secret nor the key is stored. The Apple and Android keys accept only the biometrics enrolled when biometric unlock was set up: a fingerprint or face added later makes the key unusable for good (on Apple devices a fingerprint or face removed does too), so a person who knows the device passcode cannot add one and open it. The lock screen then says that biometric unlock must be set up again, and the PIN, the passcode or the phrase unlocks. An app enrollment made before this rule accepts any biometric enrolled on the device until its next biometric unlock, which replaces its key with one under the rule; someone who added a biometric before that unlock can still open it. Windows Hello has no such rule: its key accepts any biometric enrolled in Windows Hello and the Windows Hello PIN. Removing every biometric or the device passcode leaves the key unusable or destroys it, and the PIN, the passcode or the phrase then unlocks. In a browser whose passkey provider supports the WebAuthn PRF extension, HKDF-SHA256 over the PRF output gives the key; it is derived again at each unlock and never stored. The passkey's check accepts whatever user verification the provider accepts, which can include the device password. When the passkey syncs (iCloud Keychain, Google Password Manager, a password manager), the provider account holds the credential, so the wrap is as strong as that account plus a copy of the storage. Where neither can bind (a device without a strong biometric or secure hardware, a browser or passkey provider without PRF), the app does not turn biometric unlock on. An enrollment made before that, or before the binding, can still be a presence gate: a random AES-GCM-256 key wraps the phrase and sits in local storage beside it, the biometric check decides whether the app reads the key, and a copy of that storage opens the phrase without the biometric. While a presence gate is on, a longer app lock secret does not raise the cost of that attack. In the apps such an enrollment becomes bound on its next biometric unlock where the device can bind. In a browser, where the device also holds the PIN or passcode wrap, the lock screen asks for that secret instead of starting the biometric prompt, and an unlock with it removes the enrollment, with a notice; where it is the device's only lock it stays, and Settings warns about it and offers to set it up again where the browser can bind. A phrase change never makes a presence gate for the new phrase. Settings shows which kind each device has.
- **Secret-wrapped phrase.** With app lock enabled, the phrase is wrapped with an AES key derived from the PIN or passcode (same PBKDF2 parameters and salt lengths as above) and stored in synced `UserSettings` plus localStorage. Offline brute-force of the wrapped blob recovers the **master phrase** - the root key for the whole account - which is sharper than the per-note gate and accepted: it requires a copy of a trusted device's storage, and it costs the offline search set out in "PIN protection". (In a browser the envelope needs no search at all: a copy of the whole profile carries the envelope and its key's bytes together. In the apps whose device keeps the key, a copy alone does not open the envelope, but it still carries this wrap where the device's lock is on or it keeps no phrase at rest that opens, sealed behind the same key so that the copy alone cannot search it, and a biometric enrollment that is not bound opens the phrase with no search. The app lock exists to replace the envelope with a wrap that costs a search.)

User-facing copy describes the app lock secret and an unbound biometric as gates, not encryption.

The app lock protects the phrase, not the sign-in session. A copy of a device's storage, locked or not, holds that session, which can delete or overwrite the account's notes on the server but cannot read them; on a custodial account it can also fetch the stored phrase unless two-factor sign-in is on, because fetching the phrase then asks for a code from the last five minutes. Accepted as a residual: it needs a copy of the device's files, which full-disk encryption already blocks. A copy that nobody refreshes stops working after the session's inactivity timeout (see the known limitations of the custodial section); a copy its holder refreshes, or one that can also open the phrase, does not.

## Sync, conflicts, and deletion

- **Model:** pull-then-push per device. The pull follows a server-assigned change clock; every note also carries a client edit stamp (`updated_at`).
- **Conflicts:** a push lands only on the server version the device last synced, so a device that has not caught up does not overwrite a newer version: it merges field by field against the version it last synced. A change made on one device only is kept. Text edited on two devices while apart opens a resolution dialog on the device that syncs second, and both versions are kept until the user chooses. When both devices changed the same field (a pin, a folder, a title), the field from the device that edited the note last, by that device's clock, is kept, without a dialog: a note carries one edit stamp, not one per field, so a later edit to any of its fields decides. A copy restored from a backup takes the record of the note it replaces and merges the same way. A note that already carried an unsynced change before the device began recording its synced version merges by comparing edit stamps field by field, and any difference in its text opens the dialog. A permanent delete on one device removes the note everywhere, including an edit another device made while apart and already synced; an edit that had not reached the server is kept as a new note.
- **Deletion and retention:** moving a note to the Trash is an edit like any other (the flag sits inside the ciphertext), and the note stays restorable from the Trash. Each device permanently deletes trashed notes 30 days after they were trashed, once it has pulled the account's notes and settings, unless the account has switched the Trash's auto-delete off, in which case they stay until deleted by hand. A permanent delete writes a tombstone (`deleted_at`) that syncs to other devices and cannot be undone: no client path restores a tombstone, and a trigger drops every later write to the row. The server removes the note's ciphertext and version history in the same transaction that accepts the tombstone. The tombstone itself stays, holding only the note id, the account's public key, timestamps, the delete's seal and the number of the key that made it, so a device that returns after any time offline still learns of the delete; deleting the account removes it. Encrypted files the note referenced count toward the quota until they leave storage, after a short grace period, normally one day and at most a few days. A permanent delete needs a live session (one that passed two-factor, when it is on) and no key, so a stolen session can remove the ciphertext and version history of every note from the server. It cannot remove the copies on the user's devices by that alone: the device that deletes seals each tombstone with the account key, bound to the account and the note, and every other device checks the seal before it deletes its own copy. A device refuses a tombstone whose seal does not check: it keeps the note, puts it back on the server under a new id, and tells the user. A tombstone with no seal comes from an app version before sealed deletes, or from a session without the key. For those, a device that would lose more than ten notes it still holds, shown or in the Trash, within a day keeps them and asks; keeping them puts them back on the server under new ids. Below that count, or once the user agrees to the delete, each device deletes its own copies at its next sync. A session without the key cannot set the Trash flag itself, but it can copy an older note payload that carries the flag onto other rows, and those notes then move to the Trash on every device without a question; the Trash's auto-delete removes them 30 days later unless the user restores them first. A device keeps an edit that had not reached the server as a new note either way; every other deleted note is gone unless a device kept it or the user holds an export. The version history of a deleted note is gone in every case.
- **Replaced text:** a sync cannot always tell another device's edit from an older ciphertext of the same account written over the row by a session without the key ("Known limitation: no AAD" says which ones it refuses). When a sync replaces the title or body of a note that has no unsynced change, the device keeps the text it replaced for 30 days, encrypted like the notes on the device, and the note's History offers it back on every plan; a restore is an ordinary edit that syncs. Residuals: the replacement itself still happens on every device; a change to tags, flags or folder alone keeps no copy; a note keeps at most ten copies; a device keeps only the text it held, so a device that was offline or never had the note keeps none; the copies stay on that device only, and a sign-out that removes the notes removes them.

## Deletion metadata

- Deleting an attachment queues its opaque blob id in a server-side pending set (`pending_blob_gc`), so the server learns "a blob was deleted around time T" at delete time rather than at the deferred sweep. Owner-scoped by RLS; blob contents stay encrypted throughout.

## Devices and fingerprint hashes

Each registered device has a server-side row: user-visible name, platform, last-seen timestamp, and four fingerprint hashes used to group multiple browsers on one physical machine into a single device entry. The signals - platform, GPU renderer string, CPU core count, browser language - are hashed client-side with HMAC-SHA256 under a per-user pepper derived from the BIP-39 seed. The raw GPU string, core count and language never leave the device, and the server cannot brute-force these low-entropy signals because it never holds the pepper. The operating system name does leave it: the device name sent in the same request is built from it, and the server keeps that name readable. Hashes are incomparable across users.

**Removing a device is enforced by the server.** Each sign-in session is bound to the device that uses it, when the device registers and at each heartbeat, and a session keeps the device it was first bound to. When a device is removed from another device, by an operator, or because the account went back to the free device limit, every session bound to it is marked. The session gate that every row policy, every gated function and every file request asks refuses a marked session, for every account, so with that session a removed device that ignores the removal reads and writes no note, setting or file. The removed device's own heartbeat still gets an explicit answer, which is what makes the app sign out and clear its local data; the mark is kept, not the session deleted, so a device that was offline when it was removed gets that answer when it comes back; after the inactivity timeout it gets the same answer from its next registration. A session that removes its own device (a sign-out, or the device list clearing this device's own entries) is not marked by that. The mark of a session is cleared only by a registration of the same device that carries a signature from the phrase and says it is a sign-in made on the device, or comes from an app build too old to say; a removed device also needs a free device slot to come back.

Residual: removal protects against a lost or stolen session, not against someone who holds the phrase, who can always sign in again. A session that never registered a device is not bound, so a removal does not end it, and the binding trusts the first device a session names. The holder of a marked session can still refresh it and, with a registration of the same device recorded earlier, bring the device back; without two-factor sign-in, a marked session less than a day old can also get an unmarked one through the sign-in service.

## Two-factor sign-in

Two-factor sign-in is optional. Supabase Auth verifies six-digit TOTP codes; the setup QR is rendered on the device. The server stores the authenticator secret. This is a server access control and does not change encryption: somebody with the phrase can decrypt ciphertext they already possess, and an unlocked device remains in scope for its owner. A compromised server can bypass this access control.

Enabling account management establishes one canonical Auth user for a pubkey, using the existing phrase-derived credential. The same user owns every TOTP factor. A phrase password grant reaches that user directly. An explicitly connected OAuth identity reaches it through the account-logins edge function: the native one-use PKCE exchange identifies the exact provider, the edge creates a native canonical AAL1 session, and a database transaction registers its provider origin before tokens leave the edge. Native automatic same-email linking does not make an unapproved provider connection active. Connecting a provider cannot merge two vaults or change key custody.

Protected managed-account data requires the canonical user and a live session created by the phrase password grant or an active registered provider connection. When an authenticator is enabled, the same check requires a current verified factor and a current AAL2 session, not merely an AAL2 claim in an old JWT. Restrictive policies protect client data and storage; protected SECURITY DEFINER RPCs and session edge functions apply the same gate, except a few calls that answer no account data (the session-binding nonces of `link-pubkey` and the phrase-change availability check). A browser extension or command line connected to the account uses a token of its own and does not pass this check; turning on two-factor sign-in disconnects every one connected before. A denied read of rows the account holds raises an explicit error, so sync cannot mistake refusal for an empty account; a denied read of an account or a folder that holds no row answers empty, which tells the caller nothing new. Caller-only setup/status RPCs remain available before this gate, with connected-account details withheld when access is denied. Intentionally public share endpoints and unmanaged accounts retain their existing contracts.

Account connections and factor enrollment/removal require an Ed25519 signature over a single-use, expiring challenge bound to the user, session, pubkey, operation and exact payload digest. With MFA enabled, these mutations and custody changes require a TOTP verification from the last five minutes; account deletion checks freshness before deleting data. Native factor triggers consume a factor-specific signed intent. A client calling the native API directly cannot activate or delete a verified authenticator without that proof. The verified account-deletion service has a separate, scoped factor-cleanup function. Password identity guards reject native credential replacement while permitting native database encryption rewrapping; the integration harness pins both behaviors against Auth v2.198.0. A platform Auth upgrade needs the same integration checks.

Recovery uses the reusable authenticator setup secret, named the 2FA backup key, saved outside PrivacyNotes. Setup hides the original and requires confirmation from the saved copy before activation. The key restores codes in another authenticator; it does not replace the phrase or a provider login. There is no email reset, operator recovery or alternate bypass. Losing both authenticator and backup blocks new server access. Existing locally unlocked notes remain readable and exportable. The code prompt is outside network timeouts; cancellation and service failures never wipe local data.

Disconnecting a provider removes its authorization and revokes every canonical session recorded for that connection. Before removing the current provider, the app proves the phrase login and performs fresh MFA in that session. A custodial account must keep an active provider or explicitly switch to self-custody first. Account deletion removes connections and factors but keeps a pubkey revocation tombstone, so still-valid old alias JWTs cannot regain access when the other records disappear. Reclaiming a deleted pubkey requires the phrase password proof; an old provider token is insufficient.

## OAuth users

OAuth (Google, Apple, GitHub) is an identity-only sign-in path. At first OAuth sign-in the user chooses a key custody model, on a screen that preselects custodial.

### Account identity and cross-provider linking

For accounts that have not opted into account management, account resolution is decided by Supabase GoTrue by **confirmed email**, not the provider's `sub`: a second provider reporting the same verified email merges into the same `auth.users` row, hence the same pubkey and notes. This is the load-bearing feature that lets a Google signup later sign in with Apple.

**Safety condition:** this is safe only because every enabled provider proves email ownership. Merging into a victim's account requires controlling the victim's email address, at which point most of their accounts are already lost - the standard property of email-based OAuth linking.

**Invariant (do not break):** never enable an auth method that can present an unverified email as confirmed (e.g. email/password without verification, a misconfigured magic-link path). Such a method would let an attacker merge into a custodial victim's account and call `get-custodial-phrase` to retrieve the plaintext phrase. Self-custody users would be unaffected; custodial users would be fully compromised.

**How the session credential complies:** the email provider is enabled (password grant for the re-mint credential above) with confirmation required, so a self-serve signup can never yield a signed-in, confirmed identity. The pubkey link and signed account-management activation confirm exclusively `<pubkey>@phrase.privacynotes.app` - composed server-side from a pubkey proven by ed25519 signature, on a domain the project controls and no identity provider can assert. No attacker-chosen address can reach a confirmed state through it.

**Known UX failure mode (data-loss-shaped, not a security issue):** if the second provider returns a different email (Apple's "Hide My Email" relay, or simply a different address), no merge occurs and the user silently lands in a fresh, empty account. Custodial users are hit hardest, as they are least likely to have saved their phrase. Onboarding surfaces phrase / QR recovery prominently for this reason.

### Self-custody (maximum privacy)

The phrase is generated client-side and never transmitted, except sealed under a sign-in passkey the user adds (see "Passkey sign-in"). The server stores only the pubkey under `app_metadata.pubkey`; OAuth proves identity and grants no access to key material. A new device requires the phrase or a QR sign-in from an existing device.

### Custodial (keep it simple)

The OAuth choice screen preselects this mode. A phrase account can explicitly connect a provider in Settings and then choose custody separately. Continuing with it stores the phrase server-side, encrypted with AES-256-GCM under a dedicated server secret (`CUSTODIAL_PHRASE_KEY`), enabling 1-click sign-in on new devices.

**Trust implications** (the user-facing statement is SECURITY.md's custodial section; these are the mechanics):

- The server operator, or anyone holding both database access and the secret, can decrypt the user's phrase and therefore all their data. A valid legal order could compel this. Database-only breaches stay unreadable.
- Custody is reversible from Settings > Account > Key custody: leaving deletes the `custodial_phrases` row, returning re-inserts it. Both directions require an eligible live account session AND an Ed25519 signature over a challenge, with fresh MFA when enabled, so a stolen session token alone cannot change custody mode. The signature covers a one-use server nonce bound to the session and the exact request, so a saved copy of a request cannot be sent again. Residual: while older app versions are supported, the server also accepts the older signature without the nonce (see "Challenge-response authentication"). Those signatures are checked against the account key the server has on file, and a session alone cannot move a provider login to another key while the old key still holds a stored phrase, a note or a signed-in device. Residual: a provider login with none of these (nothing written, no device signed in) can be moved to a key the session holds, which is how "start fresh" works for an empty account. Cost of reversibility: the plaintext phrase can reach `store-custodial-phrase` from any signed-in device at any time; the signature bounds who, not when or where.

**Known limitations (flagged for audit):**

- `get-custodial-phrase` requires a valid eligible session and, when MFA is enabled, a code verified in the last five minutes, but no phrase signature challenge. Without MFA, a stolen eligible session suffices to exfiltrate the phrase for as long as the session stays valid. Sessions have no timebox, so a copy that keeps refreshing stays valid until it is signed out or revoked. They have an inactivity timeout of 60 days: the sign-in service refuses a refresh made more than 60 days after the previous one. Refresh-token rotation ends the copy at the legitimate device's next refresh, so a device that stays closed leaves the window open: without limit while its copy keeps refreshing, and until 60 days after the last refresh otherwise. A copy used at once, or one that keeps refreshing, is not stopped by the timeout. A signature challenge is not straightforward here: the user may not yet hold a signing key (the phrase is needed to derive it).
- `store-custodial-phrase` checks the word count and that the phrase derives the account's signing key, so only the account's own phrase can be stored.
- Neither custodial endpoint has rate limiting beyond platform defaults, notable given what `get-custodial-phrase` returns.
- `get-custodial-phrase` records each release in one database step before it sends the phrase: the account, the time, the sign-in session and whether the phrase went out. When that step does not answer, the phrase is not sent. On a device with the app lock, a start asks the server for no phrase: the unlock opens the device's own wrap. The account's other signed-in devices read those rows and show when the phrase first went to another sign-in session, so a release to someone else can be seen; it is not stopped by that, and a device that is not opened shows nothing.
- A session more than a day old cannot set a password on its account without a code sent to the account's email; a younger session can. A password sign-in made that way is a provider account's session with no sign-in flow of the app behind it, and the stored phrase is not released to it (see "Native sign-in return address").
- The decrypted phrase transits isolate memory during `get-custodial-phrase` responses with no explicit zeroing; inherent to the runtime.

### Native sign-in return address

On iOS and on Android 12 and later a native sign-in returns to an https address that the operating system delivers only to our signed app (Android App Links, iOS Universal Links); on Android the person can still give that address to another app by hand in the system settings. No custom URL scheme is an accepted return address, because any installed app can claim a scheme. Desktop operating systems do not verify which application receives a return address, so the desktop app asks for none: its sign-in ends on a page of ours that shows a one-time code, the person pastes it into the app, and only the app that started that sign-in holds the verifier the code needs. In a phone's browser neither that page nor the page that finishes connecting a sign-in account shows a code to copy, so an app on the phone cannot ask the person to copy one out. Residual: a phone browser that asks for the desktop site and hides that it is a phone, or one that runs without scripts, still leaves the code in reach. Residual: whoever gets a person to paste that code elsewhere finishes a sign-in they started; that is social engineering (see "Out-of-scope threats"). `get-custodial-phrase` requires an eligible session and a recent code when MFA is enabled, and sends no phrase it could not record (see "Custodial (keep it simple)").

The server gives a stored recovery phrase to a Google, Apple or GitHub session, and lets such a session set the account's key, only when the sign-in behind that session returned to an address of the app. This does not stop an app that shows the provider's sign-in page in its own window and receives the password there. On Android 11 and older it also does not stop an app that starts the sign-in itself and claims our return address without verification: the system can hand that address to it.

**Historical note:** before v0.152.0, an edge function derived OAuth users' phrases server-side from a secret pepper, silently. It was removed in v0.173.4 after all affected users migrated; the explicit custodial opt-in replaced it.

## Out-of-scope threats

- **Device compromise:** OS-level malware, keyloggers, memory inspection, or storage read by code running on the device. A copy of the stored files taken without that access is in scope (see "Trust boundaries"). A hostile program running under your own user account counts as device compromise: it has the same access to the app's storage and keys as the app itself. A sandboxed app from a store does not have that access, so what it can do from inside its sandbox, such as registering a URL scheme or opening a sign-in sheet, is in scope. That is why the native sign-in return address is bound to our app on iOS and on Android 12 and later.
- **Supply-chain attacks on the web bundle:** a compromised CDN could serve malicious JS. Mitigated for desktop (bundled frontend); SRI / reproducible builds not yet implemented for web.
- **Denial of service** against Cloudflare or Supabase.
- **Clipboard exposure:** once a secret is copied, the OS clipboard is outside our control. The app makes no clipboard-wipe claim; a timed wipe from a background tab is unreliable and would be security theater. The browser extension clears a value it copied after 30 seconds if the clipboard still holds it; that is best effort and does not reach a clipboard history or a synced clipboard.
- **Social engineering** that extracts the phrase or a sign-in code from the user.
- **Quantum computing:** XChaCha20 at 256 bits is quantum-resistant; Ed25519 (signatures) and X25519 (the inbox key that clips, command line notes and login changes are sealed to) are vulnerable to Shor's algorithm, so a recorded inbox row could be opened later. Not a near-term practical concern.
